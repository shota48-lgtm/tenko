## 1-1. 建物に入れない（最優先）

### 原因

Phase 4.8 では、人物の**足元の1点**（`x+16, y+28`）が建物の枠に入るかで判定していた。
この形では、人物の左上が入れる範囲は `y = 4..35` の32ドットで、建物（`y = 32..64`）に対して
**ほぼ真上にずれている**。人物を建物に重ねて置いたとき、下向きの余裕は**3ドット**しかなかった。

つまり「建物の上に人を置く」という自然な操作では、ほぼ入れない。
POが4回試して0回だったのは操作の問題ではなく、判定の位置がずれていたためである。

### 直したこと

| 直した点 | 内容 |
|---|---|
| 判定の基準 | 足元の1点 → **人物の中心** |
| 判定の余白 | なし → **12ドット**（`ENTER_MARGIN`）。判定は 56x56 になる |
| 近い建物を選ぶ | 余白どうしが触れる配置でも、中心が近い方の建物に入る |
| ドラッグ中の表示 | いま離したら入る建物を**枠で光らせる**（満員なら赤い破線） |
| 落とした結果 | 「「オフィス」に入りました」「広場に出ました」を画面に出す。黙って置かれない |

余白を12にしたのは、建物の間隔が最短32ドット（例: `(2,2)` と `(6,2)`）で、
`32 + 12*2 = 56` なら隣の建物の判定と重ならないため。

判定範囲の実測（人物の左上が取りうる値）:

```
直す前:  y 4..35（32ドット） 建物は y=32..64 → 下向きの余裕は3ドット
直した後: y 4..59（56ドット） x 4..59（56ドット）
```

### さらに見つかった不具合: 建物に入ると出られない

案2（建物の中の人は描かない）のため、**自分が建物に入ると自分のアバターも消えていた。**
掴む対象が無いので、一度入ると二度と出られない。実機のドラッグで気づいた
（建物の上をドラッグしようとして、建物のクリックと解釈されチャットへ飛んだ）。

- **自分だけは、建物の中にいても必ず描く**ようにした（名前と吹き出しも同様）
- あわせて、アバターのメニューに「建物から出る」を置いた（ドラッグが基本、押す道も残す）

### 実測（実際のマウスドラッグ。座標指定ではない）

`left_click_drag` で、広場から3箇所へ落とした結果。

| 落とした場所 | 結果 |
|---|---|
| 屋根の中心 | `位置=(26,13) roomId=1 状態=talking` → **入れた** |
| 扉のあたり | `位置=(29,36) roomId=1 状態=talking` → **入れた** |
| 建物の少し下 | `位置=(31,56) roomId=1 状態=talking` → **入れた** |

出る側も実測: 広場へドラッグ → `位置=(81,149) roomId=null 状態=idle`（在席に戻る）。

## 1-2. 村がスクロールする

### 原因

拡大率を2倍で固定していた。村は640x416なので1280x832になる。
実測した窓の高さは935で、村を入れる枠は `calc(100vh - 6.5rem)` = 831。
**832 に対して 831 で、1ドット足りずにスクロールバーが出ていた。**

### 直したこと

- 窓の大きさから、村全体が入る拡大率を測って使う（0.05刻み。下限1.2倍）
- 全体表示のときは枠にスクロールを付けない
- 「寄る」ボタンで2倍に切り替えられる（このときだけスクロールする）。**既定は全体表示**

整数倍でないと1ドットの大きさが完全には揃わないが、
村の一覧性を失うよりは良いと判断した（PO判断が要る点として報告に記載）。

### 実測

```
直す前: 倍率=2    canvas=1280x832  縦スクロール=あり
直した後: 倍率=1.95 canvas=1248x811  縦スクロール=なし（ページ側も無し）
```

## 3-1. 吹き出しが3件しか出ない — 3案の比較

### 比較の前に見つかった不具合

**吹き出しの配置計算が、丸ごと捨てられていた。**

`bubbles.ts` は重なりを避けて位置（`b.x` / `b.y`）を決めているのに、画面側はその値を使わず、
しっぽの位置（`b.tailX` / `b.tailY`）に描いていた。さらに大きさも CSS 任せで、
計算上の箱（`b.w` / `b.h`）と実際の描画が違っていた。

つまり Phase 4.5 以降、重なり回避は一度も効いていなかった。
「3件が限界」という Phase 4.8 の判断も、この状態での判断だった。

直したこと:

- 計算が決めた位置（`b.x` / `b.y`）に置く
- 計算が決めた大きさ（`b.w` / `b.h`）で描く。文字の大きさも計算の前提に合わせる
- 名前のラベルも「置いてはいけない場所」として避ける

### 3案の比較（22人。DOMの矩形を数えた実測）

直した後:

| 案 | 吹き出しの数 | 吹き出し同士の重なり | 名前を覆った数 |
|---|---|---|---|
| 案1 常時3件 + 乗せた人 | 3 | 0 | 0 |
| **案2 全員** | **19** | **0** | **0** |
| 案3 乗せた人だけ | 0 | 0 | 0 |

直す前（参考。同じ22人）:

| 案 | 吹き出しの数 | 吹き出し同士の重なり | 名前を覆った数 |
|---|---|---|---|
| 案1 常時3件 | 3 | 0 | 3 |
| 案2 全員 | 19 | 4〜6 | 17 |

### 判断: 案2（全員）を採る

理由は、**重なりも名前の被りも0で成立するようになったため**。
Phase 4.5 で立てた「村を見れば全員が今日何をしているか分かる」が、これで初めて成立する。

全員分を出すときは1行に絞る（2行だと高さが倍になり、上の段に届く）。
長い文は末尾を「…」で切る。全文は乗せたときと、メンバー一覧で読める。

案3（乗せた人だけ）は、村を見ても誰も何も書いていないように見えるため却下した。

## 6-2. 移動の同期頻度と負荷（50人）

`node scripts\load-move.js 50 10`。50本の接続が100msごとに座標を送り、見張り1本が受け取った量を数えた。

| | 名前を配っていたとき | **名前を外した後** |
|---|---|---|
| 送った移動 | 4650件（465件/秒） | 4650件（465件/秒） |
| 受け取った在席一覧 | 93回（9回/秒） | 93回（9回/秒） |
| 受け取った量 | 757KB（1本あたり76KB/秒） | **483KB（1本あたり48KB/秒）** |
| 1回あたり | 8330バイト | **5320バイト** |

**送るのは毎秒465件でも、配信は毎秒9回に収まっている。** 50msにまとめているため、
人数が増えても配信回数は毎秒20回で頭打ちになる。

あわせて、**在席の配信から名前を外した。**
画面はDBの表示名を使うので元から要らず、外せば「自己申告の名前が他人の画面に出る」経路が
構造的に無くなる（J239・呼びかけの直しと同じ考え方）。量も 8.3KB → 5.3KB に減った。

## 11. POに判断してほしい点

1. **村の縮尺が整数倍でなくなりました**（1.95倍）。ドット絵の1ドットの大きさが完全には揃いません。全体が入ることを優先しましたが、絵の質を優先するなら「2倍でスクロール」に戻せます。
2. **吹き出しを全員分出す形にしました。** 長い文は1行に切り詰め、末尾を「…」にしています。全文を読む手段は、乗せる・メンバー一覧の2つです。
3. **部屋の見分けは、部屋名に含まれる語（開発・営業・休憩など）で決めています。** 名前を変えると印も変わります。DBの列にする案もあります。
4. 離席のまま部屋の席を占め続ける点は Phase 4.8 から変わっていません。
