## 事前確定事項

### 1. 時刻とタイムゾーン

**実測してから決めた。** `scripts/probe-timezone.js` の出力:

```
DBサーバーの timezone 設定: {"TimeZone":"GMT"}
日本時間 8/12 00:30 -> JST基準の日付 = 2026-08-12 / DB既定の日付 = 2026-08-11
日本時間 8/13 08:59 -> JST基準の日付 = 2026-08-13 / DB既定の日付 = 2026-08-12
既存の attendance_records:
  id=1 work_date=2026-08-11 JST=2026-08-11 23:51 UTC=2026-08-11 14:51
```

- **DBサーバーの既定は GMT。** 何もしなければ日付は UTC で切られ、日本時間の 00:00〜09:00 が前日に倒れる
- 既存の実装（Phase 4）は `(event_at AT TIME ZONE 'Asia/Tokyo')::date` と明示しており、**JST 基準で正しく切れていた**（id=1 が JST 23:51 で work_date=8/11。UTC基準なら 8/11 14:51 でも同日だが、JST 00:30 のケースでは差が出る）

**決定: 業務上の1日の境界は JST（Asia/Tokyo）に統一する。** タイムゾーンは環境変数 `TENKO_TZ`（既定 `Asia/Tokyo`）とし、SQL には**パラメータとして束縛**する（文字列連結しない。S2）。

- 深夜0時をまたぐ勤務: 出社が 8/12 23:00、退勤が 8/13 02:00 の場合、**それぞれの発生時刻の JST 日付で別の日に記録される**。勤務の対を作って夜勤を1日に寄せることはしない
  - 理由: 対を作るには「どの出社とどの退勤が組か」の推測が要る。給与の根拠に推測を混ぜない（Phase 4 で休憩を回数に留めたのと同じ理由）
  - **この扱いは夜勤のある職場では正しくない。要判断（POへ）**

### 2. 「今日やること」のリセット判定

**決定: サーバー時刻（JST）で判定する。クライアントから渡された日付は一切使わない。**

セキュリティ上の理由: クライアント時刻を信用すると、端末の時計をずらすだけで任意の日付として振る舞える。
「今日やること」自体の実害は小さいが、**日付をクライアントから受ける形を1つ作ると、勤怠でも同じ形を使う誘惑が生じる**。
勤怠の日付をクライアントが決められる状態は改竄そのものであるため、最初から作らない。

実装: API は `note_date` をリクエストから受け取らない。サーバーで `(now() AT TIME ZONE $tz)::date` を使う。
