## 0. いまの姿を1枚で

- **村が入口。** `/` が村で、チャットは `/rooms/[id]`
- **アバターはドラッグで動かせる。位置が状態を決める**（建物に入ると会議中、出ると元の状態）
- **会議室には定員がある**（`rooms.capacity`。house=4 / hall=12 が初期値）。判定はサーバー側
- **通話は近接音声を採らない。** 「呼びかけ → 相手が承認 → 通話」の形にする。呼びかけまで実装済み
- **勤怠が村に出る。** 未確定の下書きは頭上に印が出て、その場で確定・却下できる
- **認証が入った（Phase 5）。** Google 認証のみ。あらかじめ `users` に登録された人だけが使える
- **未ログインでも村が見える**（見るだけモード）。書き込む操作はすべてログインが要る
- **公開先は Vercel（アプリ）と Render（ws-server）。どちらも無料枠**

## 1. 目的

チャットと勤怠を繋いだオフィスアプリを実装する。
第一目的は転職。収益化は目的に含めない。

勤怠が面倒な理由は二重申告にある。
利用者はチャットで既に「10時に着きます」と報告しているのに、
勤怠システムはそれを知らないため、もう一度入力させている。

tenko では、チャットでの発言から勤怠の下書きを立てる。
確定は必ず人間が押す。機械は下書きまでしか作らない。

## 2. 画面

真上から見た平面の村。ドット絵で描く。バリアントAを採用（素朴な農村。木の壁と藁屋根、暖色寄り）。
BとCは判断の記録として残す。切り替えは src/sprites/index.ts の ACTIVE_VARIANT 1行。

**アバターはドラッグで自由に動かせる（Phase 4.8）。位置が状態を決める。**
初日に決めた「自由移動は実装しない / 状態が位置を決める」は、POの判断で入れ替わった。
3D は採用しない。実測の結果、同種のサービスが2次元で成立しているため。

動かせるのは自分のアバターだけ。移動の可否・座標の範囲・部屋の定員は、
すべて ws-server が判定する（画面側の判定だけでは、WSを直接叩けば通るため）。
**誰として村にいるかは入場券が決める**（Phase 5 段階6）。メッセージが名乗る利用者IDは読まない。

村の要素と意味:

| 要素 | 意味 |
|---|---|
| 建物 | 部屋（rooms の1行 = 1棟）。kind で house / hall を決める。定員は rooms.capacity |
| 建物に入る | **その部屋で会議中になる。** 出れば入る前の状態に戻る |
| 建物の中の人物 | 描かない。乗せると部屋名・人数・中の人の名前が出る。**ただし自分だけは描く** |
| 建物の窓が光る | 誰かがその部屋にいる |
| 建物の下の帯 | 何人入っているか。0人・途中・満員（赤）が区別できる |
| 建物の赤い枠 | 満員 |
| 建物の屋根の下の印 | 部屋の性格。**`rooms.deco` の値だけで決まる**（Phase 4.10）|
| 建物の屋根の上の旗 | その部屋に未読の投稿がある |
| 自分の頭上の「勤怠 N」 | 確定していない勤怠の下書き。押すと確定・却下できる |
| 自分のアバターの金の枠 | 自分。50人いても探せるようにするため |
| 広場 | どの部屋にも入っていない状態 |
| 噴水 | 村のお知らせ。押すと開く。書けるのは admin のみ。**未ログインには中身を見せない** |
| 村の外 | 退勤 |

選べる状態は 在席 / 離席 / 休憩中 / 退勤 の4つ。
**「会議中」はメニューから外した。** 選ぶものではなく、建物に入った結果になったため。

## 3. 実測にもとづく設計方針

spike\ws-01（2026-08-11）と spike\ws-auth-01（2026-08-13）の実測より確定。

- WebSocket の切断中の送信は、例外もエラーも出さずに消える
- 自動再接続は成立する。バックグラウンド3分でも接続は維持される
- **ブラウザの WebSocket は独自のヘッダを送れない。** 別ドメインには Cookie も届かない
- **`Sec-WebSocket-Protocol` で券を運べる**（138文字が欠けずに届く）
- **券の符号化にパディング（`=`）を入れてはいけない。** ブラウザが接続を試みもしない
- **ハンドシェイクで断ると close code が届かない**（1006 になる）。受け入れてから閉じる

| データ | 経路 | 理由 |
|---|---|---|
| チャットの投稿 | HTTP + DB を正 → WS で通知 | 消えては困る |
| 勤怠の申請・承認・記録 | HTTP + DB のみ | 給与に直結する |
| 在席状態 | WS のみ | 失っても取り直せる |
| **デモ用の在席** | **DB → 最初のHTMLに載せる（＋WSでも配る）** | ws-server が寝ていても村が空にならないように |

## 4. 勤怠イベントの検出範囲

Phase 3 で実装。出社 / 退勤 / 休憩 / 遅刻 の4種類に限定する。
有給・早退・直行直帰・残業申請は範囲外。検出は下書きを立てるまで。確定は人間が押す。

## 5. 認証（Phase 5）

- **Google 認証のみ**（Auth.js v5 `next-auth@5.0.0-beta.32` + `@auth/pg-adapter@1.11.3`）。
  パスワードを1文字も扱わない
- **あらかじめ `users` に登録されたメールアドレスの人だけが中に入れる。**
  未登録は `signIn` で止まり、**DBに1行も作られない**（実測で確認）
- セッションは**DB方式・7日**。JWTにしない（退職者を即座に締め出せることを優先）
- 最初の管理者は環境変数 `TENKO_ADMIN_EMAILS`
- **権限は既存の `users.role` / `manager_id` が持つ。** 認証の提供元には持たせない
- **利用者を決めるのは `currentActor()` だけ。引数を取らない**ので、
  リクエストから利用者IDを渡す経路が構文の上で存在しない
- **WebSocket は入場券で守る**（段階6）。券は `POST /api/ws-ticket`（認証必須）で取り、
  `Sec-WebSocket-Protocol` に載せる。base64url・パディングなし・60秒・使い捨て

### 見るだけモード

未ログインに開いているのは**4経路だけ**（`/api/rooms`・`/api/users`・`/api/notes`・`/api/demo-presence`）。
**未ログインに返すのはデモ用の利用者の分だけ**（実在の人の表示名も「今日やること」も返さない）。
勤怠は読み取りも含めて全閉。`TENKO_PUBLIC_VIEW=0` で見るだけモードごと止められる。

### デモ用の利用者

56人のうち50人を `is_demo` にし、**20人を村に出す**（`demo_presence` の行がある人だけ）。
残りは一覧には出るが村にいない。**接続を持たない。常時動くプロセスも作らない。**
「今日やること」は日付を持たない列に入れてある（日が変わっても吹き出しが消えないように）。

#### 漂い（2026-08-13 に解決）

**デモの人は動いて見える。ただし動いているのは絵だけで、サーバーの座標は1バイトも変わらない。**

- 方式は**画面側の決定的な漂い**。`demo_presence` の x, y を拠点とし、時刻と id から
  正弦波で変位を出す（周期は X 24秒 / Y 31秒）。**乱数は使わない。**
  同じ id と同じ時刻なら、どの画面でも同じ座標になる
- **ws-server にも DB にも一切触らない。** したがって
  **未ログインでも、ws-server が停止していても動く**
- 動くのは「デモ かつ 部屋にいない」**12人**。会議中のデモ6人と実在の利用者は動かない。
  拠点が村の端にある id18・id20 は、安全な振幅が取れないため動かさない
- 振幅は拠点ごとに 40px から 4px 刻みで下げ、**建物・噴水・村の外に一切かからない**最大値を採る。
  判定は既存の関数を再利用する（`buildingForAvatar` / `hitFountain` / `clampToVillage`）。
  同じ判定を書き起こすと、片方だけ直したときに食い違うため
- 実装は `src/village/demo-drift.ts`（新規）と `src/app/village-client.tsx`
- 検証: 判定関数を毎フレーム呼び、**のべ3,000,000点で違反ゼロ**。
  描画性能は 1.0ms → 1.0ms（**1.00倍**）

#### 撤回した方針: ws-server の60秒周期に相乗りさせる

当初は「ws-server が既に持つ60秒の周期で座標を書き換える」設計だった。**撤回した。**
蒸し返さないために理由を残す。

1. **ws-server は DB を持たない**（依存は `ws` のみ）。座標の保存先が無い
2. **WS の入場券は認証必須。** 未ログインの閲覧者に配信が届かず、目的そのものを達成できない

判断は `JUDGMENT_HEURISTICS.md` の **J256** に記録済み。

## 6. 技術構成

- Next.js 16.3.0（バージョンは固定値でピン留め）
- TypeScript / PostgreSQL（Neon）
- WebSocket サーバーは ws-server ディレクトリに分離。素の Node.js + ws
- **デプロイ先は Vercel（アプリ）と Render（ws-server）。どちらも無料枠**
  - Railway は「常時起動には無料枠が足りない可能性が高い」ままだったため、
    2026-08-13 に **Render へ変更**（PO判断。カード不要で、WSのメッセージが停止を先送りする）
  - **費用は一切かけない。** 有料プランへの移行が必要になったらそこで止めて判断する
  - 常時起動させるための定期ping は行わない（規約と competing する手は採らない）

## 7. 実測値（2026-08-13）

### 本番（https://tenko-eight.vercel.app）

**関数はシンガポール（`sin1`）で動かしている。** DB（Neon）も同じ地域。
地域は `vercel.json` の `regions` で固定する（画面の設定だけでは効かなかった。下記）。

| 項目 | 値 | 備考 |
|---|---|---|
| 未ログインで村が出るまで（最初のHTML） | **中央 127ms**（15.8 KB） | 手元のPCから測った値。往復を含む |
| セッション確認（`/api/me`） | **中央 119ms** | 内訳は下 |
| ├ DBを引かない分（往復＋関数の起動） | 113ms | Cookie なしの `/api/me`。**ほぼ手元→シンガポールの距離** |
| └ **DBを3回引く分** | **約 11ms**（1回あたり 約3.7ms） | `auth()` の2クエリ + `users` の1クエリ |
| 参考: `/api/rooms`（DBを1クエリ） | 110ms | |
| 最初のHTMLに載るデモ用の人数 | **20人** | ws-server が寝ていても見える |
| アプリの呼び出し回数 | 1日あたり最大 2880 回 | ws-server が寝ている間は0回。認証済みの接続が0本なら `ws-verify` は投げない |

### 地域を揃える前（記録として残す）

| | iad1（米国東部） | sin1（シンガポール） |
|---|---|---|
| セッション確認 | 1077ms | **119ms** |
| うちDBの3クエリ | 862ms | **11ms** |
| 村が出るまで | 648ms | **127ms** |

**Vercel の既定の地域は米国東部。** DBはシンガポールにあったため、
1クエリごとに太平洋を往復していた（1回あたり約290ms）。

**設計書5節の見積「同じ地域なら 2〜10ms」は正しかった。**
測った 1077ms を見て「見積が2桁外れている」と判断しかけたが、
**外れていたのは見積ではなく、前提（同じ地域）が満たされていないことだった。**
数字が合わないときは、まず**見積に付いていた条件が成り立っているか**を確かめる。

役割を毎回DBから引き直す判断（降格が即座に効く）は、**11ms で買えているので変えない。**

### Render の停止と起動（無料枠）

| 項目 | 実測 |
|---|---|
| 15分の無通信で停止するか | **する**（16.6分の放置で停止） |
| 停止中に村が見えるか | **見える**（最初のHTMLに20人が載っている） |
| 起動にかかる時間 | **12.5秒**（起きている状態は 0.3 秒。公表値は「約1分」） |
| WebSocket の接続だけで起きるか | **起きる**（HTTPを叩く必要がない） |
| 誰かが村にいる間 | **停止しない**（接続2本のまま75分） |
| ws-server の外向きの通信 | **停止を妨げない**（受信だけが数えられている） |

### 本番の WebSocket で分かったこと（プロキシの性質）

| こと | 実測 |
|---|---|
| `Sec-WebSocket-Protocol` は通るか | **通る**（券つきで `[open] 認証済み` が出た） |
| 断りの知らせ（`auth.rejected`） | **254ms** で届く |
| `close(4003)` | **20,254ms 後**に届き、**code が 1006 に置き換わる** |
| 接続が閉じてから ws-server が気づくまで | 10〜20秒（乱暴に切った場合も同じ） |

**close code を当てにできない。** 繋ぎ直しの引き金は知らせのメッセージにしてある。

## 既知の穴・未確認

まだ調べていない、または直していないもの。**「確認する」ではなく「踏む可能性がある」ものとして扱う。**

### `/api/notes` の呼び出し頻度（優先度: 高・未調査）

開発サーバーのログで、`/api/notes` が短い間隔で連続して呼ばれていることをPOが目視した。
閲覧者1人あたりの呼び出し回数が **Vercel の無料枠に直接効く**ため、
「Vercel 無料枠の上限確認」は単なる確認ではなく、**実際に踏む可能性のある問題**として扱う。
ポーリングの間隔がどう実装されているかは未確認。

### `pg` の SSL モードの扱いが将来変わる（優先度: 中・未対応）

開発サーバーのコンソールに `pg-connection-string` の警告が出ている。
現在 `prefer` / `require` / `verify-ca` は `verify-full` の別名として扱われているが、
**`pg` v9.0.0 以降は標準の libpq 準拠になり、検証が弱くなる。**

**`pg` を上げるときは、事前に `DATABASE_URL` に `sslmode=verify-full` を明示すること。**
Vercel の環境変数とローカルの `.env.local` の両方を更新し、再デプロイが必要（PO職掌）。
