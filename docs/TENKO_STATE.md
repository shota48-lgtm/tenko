# TENKO_STATE

最終更新: 2026-08-11

## 1. 目的

チャットと勤怠を繋いだオフィスアプリを実装する。
第一目的は転職。収益化は目的に含めない。

勤怠が面倒な理由は二重申告にある。
利用者はチャットで既に「10時に着きます」と報告しているのに、
勤怠システムはそれを知らないため、もう一度入力させている。

tenko では、チャットでの発言から勤怠の下書きを立てる。
確定は必ず人間が押す。機械は下書きまでしか作らない。

## 2. 画面

真上から見た平面の村。ドット絵で描く。バリアントAを採用（素朴な農村。木の壁と藁屋根、暖色寄り）。
BとCは判断の記録として残す。切り替えは src/sprites/index.ts の ACTIVE_VARIANT 1行。

在席状態に応じて人物が自動で配置される。自由移動は実装しない。位置は状態が決める。
3D は採用しない。実測の結果、同種のサービスが2次元で成立しているため。

村の要素と意味:

| 要素 | 意味 |
|---|---|
| 建物 | 部屋（rooms の1行 = 1棟）。kind で house / hall を決める |
| 建物の中の人物 | その部屋で会話中 |
| 建物の窓が光る | その部屋で会話が起きている |
| 広場 | どの部屋にも入っていない状態 |
| 噴水 | お知らせ（Phase 2.5 で実装） |
| 村の外 | 退勤 |

### 実装しないと決めたもの

- 家の中の内装: 部屋が増えるたびに内装が必要になり、会話までの手数も増える。建物をクリックしたらチャットが開く形を維持する
- レイアウトの編集機能: 各自が違う配置を持つと「あの家にいる」が通じなくなり、一覧性が失われる。編集画面自体が10〜15hの別機能になる
- アバターのクリック移動・自由移動: 遊びの方向に引く。位置は状態が決める
- 村のスクロール: 全員の位置が一目で分かることがこの画面の価値。村のサイズを固定し、配置密度で吸収する

### 先送りしたもの

- 会話中の点滅: 頭上の点3つが実寸で見えにくい。1つ→2つ→3つと順に光らせて視認性を上げる。既存スプライトの分割のみで実現でき、新規の絵は不要。Phase 5 の仕上げで行う
- 広場での会話の表現: 建物の中でも広場に散らばっているのでもない「2人で軽く話している」状態がない。ベンチのような場所を置くのではなく、話している者同士を隣り合わせて配置し、関係を配置で示す。1対1の会話という概念がデータ設計に無いため、Phase 3 の後に設計する
- 部屋数が増えた場合の村の広さ: 現在640×416で画面に収まる。部屋が増えて収まらなくなった時点で再検討する

### 対応していないと明記するもの

- **深夜0時をまたぐ勤務**: 勤怠は発生時刻の日本時間の日付で記録するため、出社と退勤が別の日の記録になる。夜勤のある職場では正しくない。直すには「勤務日」の概念が要り、記録・月次・承認のすべてに影響するため未対応のままにする。README.md にも記載
- **認証**: 未実装。TENKO_TRUST_USER_PARAM=1 のままでは誰でも他人になりすませる。WebSocket サーバーには認証の口がない
- **自動離席の10分**: 仮説であり、実運用での裏付けはない

### Phase 4.5 で入れたもの

- 今日やること（吹き出し）: 1人1日1行。履歴なし。日付はサーバー（JST）が決める。村では常時3件まで表示し、残りは頭上の印
- 話しかけてOK / 後でならOK / 集中中: 在席とは独立した軸。WSのみ。ドット絵は増やさず足元の点で表す
- 自動離席: 操作が10分ない場合に away へ。idle への自動復帰はしない（人がいることを機械が主張しない）
- 勤怠異常の提示: 退勤なし / 長時間 / 出社なしの発言。読み取りのみで自動修正しない
- 勤怠の修正申請: 新しい記録として立て、元の記録を指す。承認は Phase 4 の仕組みを再利用
## 3. 実測にもとづく設計方針

spike\ws-01（2026-08-11）の実測より確定。

- WebSocket の切断中の送信は、例外もエラーも出さずに消える
- サーバーログにも残らない
- 自動再接続は成立する
- バックグラウンド3分でも接続は維持される

したがって:

| データ | 経路 | 理由 |
|---|---|---|
| チャットの投稿 | HTTP + DB を正 → WS で通知 | 消えては困る |
| 勤怠の申請・承認・記録 | HTTP + DB のみ | 給与に直結する |
| 在席状態 | WS のみ | 失っても取り直せる |

## 4. 勤怠イベントの検出範囲

Phase 3 で実装する。最初は4種類に限定する。

- 出社
- 退勤
- 休憩
- 遅刻

有給・早退・直行直帰・残業申請は範囲外とする。
4種類でも「チャットが勤怠になる」という主張は成立するため。

検出は下書きを立てるまで。確定は人間が押す。

## 5. 技術構成

- Next.js（バージョンは固定値でピン留め）
- TypeScript
- PostgreSQL（Neon）
- WebSocket サーバーは ws-server ディレクトリに分離。素の Node.js + ws
- デプロイ先は Vercel（アプリ）と Railway（WSサーバー）を想定

Railway の無料枠は月1ドル分のクレジットであり、
常時起動するサーバーには足りない可能性が高い。
Phase 5 の直前に実測し、金額が判明した時点でPOが判断する。
